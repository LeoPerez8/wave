## Recommendation preparation: traced paths

- Discover: `apps/mobile/src/home/mixKnown.ts:48-74` reads multi-value song genres, Library songs/artists, counted plays, played recording keys, streamed songs and playlisted songs. `mixIndexes` shares its result for a minute. `home/discoverMixes.ts:183-204` obtains `mixCatalog`, `artistGraphNow`, global taste and a Library genre lookup, then keeps a per-section reader whose identity includes variety/catalog/graph/taste/Library. `home/discoverMixes.ts:149-164` walks each seed with JS yields before slider-dependent ranking. This serves reranking and globally known-song exclusions, not merely reading common fields.
- Magic Queue: `apps/mobile/src/playback/magicQueueRadio.ts:157-191` obtains the shared graph/catalog, but passes session state, taste, Library matching, cached audio, connectivity/mobile allowance, refill and retry time into `magicCatalogRead`. `playback/magicCatalogRead.ts:71-102` chooses cached-only playback offline and decides whether to refill online. `magicQueueRadio.ts:127-128` and `home/mixHarvest.ts:278-279` invalidate graph/catalog after radio work. `home/artistGenres.ts` intentionally distinguishes `mixProfileOf` (known Library profile, including null) from `magicProfileOf` (fallback to looked-up profile when Library genre is absent).
- Playlist: `apps/mobile/src/library/PlaylistRecommendations.tsx:41-57` combines the store's fresh snapshot with the existing graph and read-only looked-up profiles. `library/db/playlistRecommendations.ts:17-84` reads current membership, availability, favorites/downloads, catalog and feedback scoped by playlist ID. It does not request network fill or read global taste. `packages/core/src/playlistRecommendations.ts:160-169` uses the same `recommend` engine with playlist genre matching, own-track genre profiles and zero taste/newness/popularity/variety weights. Recording deduplication and scoped adjustments remain Core decisions. `library/db/playlistRecommendations.ts:113-153` keeps membership and positive feedback in one real transaction.

## Deletion tests and conclusion

1. **Confirm deferral of a universal preparation module (high confidence).** Deleting a proposed wrapper would leave actual catalog/graph service calls plus policy-specific construction. It would not remove three copies of one substantive algorithm: the shared ranking and recording-matching algorithms already exist. A wrapper that standardizes all caller inputs would need switches/options for cached-audio availability, global known-song exclusions, taste, refill, freshness and playlist feedback. Those policies would remain elsewhere or be moved into that wrapper. There is no demonstrated reduction in knowledge callers need. Keep the current graph/catalog seams and the shared Core engine.
2. **Qualify the report's shared-read claim after #558 (high confidence).** Playlist preparation does _not_ use `mixCatalog` or `mixIndexes`; it calls `selectCandidateCatalog` directly on every input read (`library/db/playlistRecommendations.ts:84`). On a cold graph read, `home/artistGraph.ts:31` also reads the catalog. Thus the integrated paths do not share every expensive read. Reusing Discover's one-minute complete snapshot would also import global known-song exclusions and stale status data, contrary to playlist semantics. This observation does not establish phone latency or warrant a cache rewrite.
3. **Narrow possible deepening candidate, independently observed (worth exploring; not a measured defect).** `acceptPlaylistRecommendation` calls the complete preparation read at line 114 but uses only its `library` and `playlist` fields for availability/membership validation (124-135). Catalog, pending favorites and prior feedback are not inputs to that validation. A tiny `traceQueries` SQLite probe showed successful Add executing unfiltered SELECTs over both `candidate_songs` and `candidate_radios` inside the transaction. The session then performs its fresh preparation read again for refill (`playlistRecommendationSession.ts:68`). Deletion test: removing recommendation-only data from the _acceptance validation read_ would remove actual queries while preserving transaction ownership; it needs no universal reader or LibraryStore split. Any follow-up should preserve recording/video identity, download-arrival handling, duplicate protection and feedback rollback through the existing real-store public API tests. No timing gain or release blocker is inferred from the query trace.
4. **Confirm rejecting LibraryStore splitting by size (high confidence).** New service methods at `library/LibraryStore.ts:535-550` expose domain operations while the SQLite transaction lives in the persistence module and ranking lives in Core. Deleting that service seam scatters Effect/error adaptation; splitting it by line count supplies no observed simplification. The extra unused full-snapshot reads above are addressable at the bounded query seam.
5. **Confirm #564's metadata correction (high confidence).** `packages/core/src/settingsPages.ts:54-106,124-129` retains literal values with `as const satisfies`; `apps/mobile/src/app/(tabs)/_layout.tsx:22` retains the known TAB_PATH union during enumeration. Deleting the widening preserves runtime behavior and restores information. Deleting the metadata registries would force consumers to own route knowledge. No additional route registry is justified.

## Required smell baseline

Checked against actual preparation paths rather than file length:

- Mysterious Name: local `readerOf`, `mixIndexes`, `magicCatalogRead` and `playlistRecommendationInput` describe different observable jobs; no supported rename finding.
- Duplicated Code / Repeated Switches / Shotgun Surgery: repeated service acquisition and snapshot construction are present, but shared matching, ranking and graph rules already have owners. Different policy lifetimes prevent asserting a universal extraction is beneficial. The redundant validation read is separately identified above.
- Feature Envy / Message Chains / Middle Man: the service-to-query delegation is a real Effect/persistence boundary; no demonstrated caller-side ownership leak or removable delegation-only layer.
- Data Clumps / Primitive Obsession: repeated graph/catalog/profile fields correspond to the existing recommendation-source contract. The integrated playlist adapter maps Library IDs into temporary engine candidate IDs, then maps results back locally (`playlistRecommendations.ts:150-173`); this is bounded adaptation, not evidence for a new ID framework.
- Divergent Change / Speculative Generality / Refused Bequest: no substantiated finding in the inspected paths. Playlist writes/reads serve one domain; no unused universal abstraction or discarded inheritance was introduced.

These are judgments, not hard standards violations. No refactoring by size or tooling-enforced complaint is proposed.

## What was checked

**Tool behaviour** (`scripts/ci/release-source.test.ts`, 16 tests, and
`scripts/ci/publish-release.test.ts`, 7 tests). Verified, POSIX run in WSL Ubuntu (Node 24.22.2):

- A sealed full build gives a manifest whose every link to this repository names the source
  SHA. A repack also names its native base, and a repack with no base or a base for another
  runtime version is refused.
- A record that isn't sealed (no `signedSha256`), has no tag, has a non-SHA source, or whose
  tag doesn't name the app's version is refused. A promotion gets the tag's stable version and
  its version code.
- Fields the contract doesn't name never reach the manifest (a test puts a password-shaped and
  a token-shaped field in the record and checks neither appears).
- `verify` reports a tag on another commit, a missing build input, a base outside the source's
  history, a version that doesn't match, and a link that names a branch.
- `publish-release.sh` attaches `wave-<version>.source.json` and `.source.md` and appends the
  directions to the notes, and attaches neither when not given them.
- The release job's new steps run only when `vars.RELEASE_SOURCE_DELIVERY == 'on'` and the run
  releases a tag, sit after sealing and before publishing, check out the gate's SHA without
  persisted credentials and name no secret.

**Every release already published.** Verified: for all 140 `v*` tags, `legacy <tag>` built a
manifest and `verify` passed (tag on the source commit, version matches, build inputs present).
The four earliest tags (`v0.5.0`, `v0.5.1-ti`, `v0.5.3-ti`, `v0.5.3`) kept their version in
`app.config.ts`, which the tool reads. 101 of the 140 have a `pnpm-lock.yaml` other than the one
the inventory read, and their manifests say their notices need their own snapshot. These
manifests were written to a local scratch folder, not committed and not attached anywhere.

**Independent build without production secrets.** Verified for the JavaScript side of
`v0.68.0-ti` (`8794eb19`), the newest release:

- Fresh `git clone` into the WSL home, outside the Windows checkout, run under `env -i` with only
  `HOME`, `USER`, `PATH` and `LANG` set. No variable name containing token, secret, key,
  password, turso, cloudflare or keystore was present.
- `pnpm install --frozen-lockfile` succeeded. The WSL account already had a pnpm store, so this
  wasn't a cold download.
- `pnpm --filter @wave/core test`: 5,210 passed, 0 failed.
- `scripts/ci/export-update.sh` (`expo export`, the over-the-air update CI publishes) succeeded
  in 2 min 37 s. Its app config says version `0.68.0-ti`, runtime version `unstamped`, updates
  disabled, and `extra` holds only `syncUrl`, `googleWebClientId`, `facebookAppId` and `router`,
  all public values. Folder digest (`release-gate.ts digest`):
  `fe30d65d41d221479e3c6bf45fc9fbad16702ad51616712075047c26b96e8bfd`. It was not compared
  with the published update; the spec doesn't ask for identical hashes.

The CI workflow text already shows the Android job runs with no secret
(`scripts/ci/release-environments.test.ts`, passing).

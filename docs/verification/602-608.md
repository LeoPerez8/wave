## Diagnosis (source inspection plus desktop measurement)

The owner's ~1,000 ms is an estimate; no owner APK, seed playlist or device trace was available. On the source at `3379e99f`, one Add ran as a single uninterrupted block of JavaScript:

1. The tap handler called the store write synchronously (`session.accept` → `save` before its first `await`; the store is synchronous SQLite under Effect), so the published `pending` state could not render until the write returned.
2. `acceptPlaylistRecommendation` validated by re-reading and projecting the **whole Library** (`trackQuery` of every song, artist/genre/favorite/video maps, a recording finder over the Library) and checked existence with `selectPlaylist`, which reads every entry and the mosaic covers. `dismissPlaylistRecommendation` and the input read used the same `selectPlaylist` check.
3. After the write, `playlistsChanged` re-read the remembered playlist list in the same task; the open playlist's query re-read on a later timer (`sharedQueries`).
4. The refill's input read and Core ranking then followed through microtasks only, with no task boundary, so the write, read and ranking were one block.

Changes:

- **Core session** (`packages/core/src/playlistRecommendationSession.ts`): the tap publishes `pending` and `pendingSlots: [index]` before any work, then hands the thread back through `yieldTurn` (`PlaylistRecommendationTurn`): `"paint"` before the write, `"free"` before the replacement's read, `"paint"` again between the read and ranking (full and refill-only renewals rank on their own turn too). Without a host hook the steps run as before (synchronous save start). A failed replacement records `unfilled` slots; a refill-only retry shows placeholders for them and never saves again, and the next Add/Dismiss's refill fills them as well.
- **App host** (`PlaylistRecommendations.tsx`): `"paint"` = `afterPaint` (two `requestAnimationFrame`s, so a whole frame can commit and paint the placeholder); `"free"` = the existing `freeTurn` (after touches/scrolls, 2 s at most). Ranking speed and stepwise yielding stay #599's.
- **Store** (`db/playlistRecommendations.ts`): a one-row live-playlist check replaces `selectPlaylist`; Add of a Library offer projects only that song (catalog offers still match against all available Library recordings, which the fuzzy recording match needs); the playlist's own entries are still read for the duplicate check.

None of these numbers are Android frame times.

Work counts are covered by a test: one Add plus one Dismiss read the same rows with a 20- and a 400-song Library, and Dismiss reads exactly 2 rows.

## UI behaviour (source only, not rendered)

- The tapped slot becomes `ControlledTrackRowSkeleton` (TrackRow skeleton plus two 48 dp control cells; still, so reduce motion is respected), accessible as busy with "Adding <song>" / "Dismissing <song>", which is also announced. The other offers keep their keys, place and enabled look; their taps are ignored by the session while it works.
- The replacement fades in (`FadeIn`, 300 ms; none with reduce motion). Results are announced (added/dismissed plus the next title, "No more matching songs right now.", or "Couldn’t load another recommendation."). An exhausted slot leaves the list; an empty list shows the existing note. A failed replacement keeps a row of the same height with Try again; a failed save restores the offer with the existing message.
- `PlaylistItems`: `maintainVisibleContentPosition={{ minIndexForVisible: 2 }}` is set only while the recommendations' top is above the viewport bottom minus the chrome inset (a Reanimated reaction on the existing scroll offset). The head, the rows/empty note and the recommendations are each a non-collapsable native view, so index 2 is the section.

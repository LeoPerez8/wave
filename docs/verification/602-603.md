## Actual baseline integration

The menu integration already exists in this baseline. `MiniPlayer.tsx` wraps its artwork/title/artist `Press` with a horizontal skip pan and an outer upward-opening pan. That `Press` has `onLongPress={openPlayingActions}`; the separate play/pause and next buttons do not open this menu. The pill is the measured anchor and highlight.

`openPlayingActions` in `ActionsMenu.tsx` reads the current queue entry. A Library song loads through `openTrackActionsById` with `playing: true`; a streamed song goes through `openYtSongActions` with the same flag. Library song lookup and native anchor measurement can complete asynchronously. The menu omits Play Next/Add to Queue for the playing song.

`Press` claims the held finger at the long-press threshold, before measuring its anchor, then forwards touch move/end/cancel to the held-touch stream. `MenuChoices` and `useSlideToChoose` consume that stream and measure options in window coordinates. `OverlayHost` draws the menu at the app root in the same window, potentially over the floating chrome. Opening this view does not transfer the original touch from its `Press` to the menu.

At baseline neither Mini player native pan consulted held-touch state. Their UI callbacks could still translate the Mini player or Now Playing sheet, and their queued JS callbacks could begin/settle the sheet or skip. This is a source-supported conflict path, not proof that either recognizer won on the owner's phone.

## Implementation

- Claiming a held menu increments a Core ownership revision. Releasing/cancelling clears the hold but never makes the originating player's revision valid again.
- The Mini player synchronously observes that state and supplies a shared `enabled` value to **both** native pan recognizers. Every UI movement and scheduled JS begin/end/skip also validates its captured revision. A hold resets the pill's offset and settles any opening drag closed. Native cancellation settles an ordinary upward drag closed rather than interpreting its cancelled velocity as an opening swipe.
- This uses the installed Gesture Handler 3.2.1 API: `CommonGestureConfig` accepts shared values, and Android `GestureHandler.isEnabled` cancels an attached handler when its enabled state changes. The public [pan configuration documentation](https://docs.swmansion.com/react-native-gesture-handler/docs/gestures/use-pan-gesture/#enabled) describes disabling recognition. Source/API inspection is not device gesture evidence.
- Closing/dismissing the frontmost overlay (including Android Back) or covering it with a follow-up cancels the held stream. Overlay interaction revisions also prevent a pending option measurement choosing an old card after it has closed or been covered, even if it later becomes frontmost again.
- The menu event consumer keeps slide highlighting, selection haptics, release outside/no slide leaving the menu open, and once-only selection. It is extracted behind a public callback interface so tests can control delayed native measurement results without mocking component internals.
- Product rule: `docs/spec.md`, Mini player and Now Playing, story 37a.

## Verification

A second agent reviewed the first implementer's uncommitted work against #603 and reran every check below on the final tree (node v26.8.2, existing `node_modules`; no install or network was needed). Review findings: the Core ownership revision, the shared `enabled` value, the per-callback revision guards and the overlay revisions match the acceptance criteria; no long-press `Press` renders inside an overlay card, so cancelling the held finger when a card opens over another one cannot break an ordinary long-press menu. The one addition was registering `playerTouchAllowed` in Core's `worklets.test.ts`, since the Mini player calls it on the UI thread.

- `node --test apps/mobile/src/overlay/slideToChoose.test.ts`: **5/5 passed**. These exercise the real held-touch stream and the menu's public event consumer: synchronous ownership notification, upward highlighting with ticks, an option over Mini player coordinates, one action despite a duplicate release, release without sliding or outside every option, cancellation, out-of-order measurements, and a release measured after the card stopped being interactive.
- `node --test src/menuTouchOwnership.test.ts src/worklets.test.ts` in `packages/core`: **18/18 passed** (ownership revisions; the `"worklet"` directive on `playerTouchAllowed`).
- `pnpm test` in `apps/mobile`: **511/511 passed**.
- `node --test` in `packages/core`: **3,358/3,358 passed** (the wall-clock tests that failed under load in the first implementer's run passed here).
- `pnpm --filter @wave/mobile typecheck` and `pnpm --filter @wave/core typecheck`: passed.
- `pnpm exec oxlint` (1.87.0) over the changed TypeScript/TSX files, `pnpm exec prettier --write` over all changed files (no changes) and `git diff --check`: clean.
- `pnpm --filter @wave/mobile exec expo export --platform android --no-bytecode --no-minify --max-workers 2 --output-dir /tmp/wave-603-export`: passed. In the emitted bundle, Core's `playerTouchAllowed` is compiled as a worklet factory (`menuTouchOwnershipTs1Factory` with `_worklet_..._init_data`), so the Mini player's UI-thread guards can call it. This is an unoptimized JS bundle, not an APK; Hermes bytecode was not compiled.

Automated callback and decision tests aren't evidence of native responder arbitration, touch delivery, visual highlighting, Android Back delivery or physical gesture behavior. That Android cancels a Gesture Handler that is disabled mid-touch comes from reading the source (`GestureHandler.isEnabled` in 3.2.1), not from observing it on a device.

# #1132 — Publishing permissions and public update exposure

Part of the security readiness spec (#1122). Verified on 2026-11-17 with read-only calls: GitHub
metadata through `gh api`, Cloudflare metadata through the owner's local wrangler OAuth session,
and GET/HEAD requests to the public Worker. Nothing was written, rotated, deployed or changed at
either provider. This record holds no credential value, account id or email address; the
`workers.dev` subdomain below is already public in `apps/mobile/app.config.ts`.

**Verdict: not a readiness pass.** The bucket and the Worker's public routes pass. The CI
Cloudflare token's actual permissions could not be read, so that essential finding stays
**unknown** and needs either the owner's token metadata or a named exception (see the end).

### 1. The credential, its consumers and its environments — pass

- Category: Cloudflare API token, `CLOUDFLARE_API_TOKEN`, with the public identifier
  `CLOUDFLARE_ACCOUNT_ID` beside it. Neither is a repository secret: `gh api .../actions/secrets`
  lists none at repository scope.
- Both exist only as secrets of the `ti` and `main` Environments. GitHub reports them created on
  2026-11-07 (00:17 UTC) in both and never updated since.
- `ti` admits deployments from branch `main` only, with no reviewer. `main` admits branch `main`
  and tags `v*`, and requires LeoPerez8's approval (self-review not prevented).
- Consumers: the release job in `.github/workflows/ci.yml` (`publish-notes.ts`,
  `publish-apk.ts`, `publish.ts`) and `.github/workflows/rollback.yml` (`promote.ts`). All go
  through `apps/updates/scripts/bucket.ts`, which runs `npx wrangler@4 r2 object put|get|delete`
  on bucket `wave-updates` only and keeps `UPDATES_SIGNING_KEY` out of wrangler's environment.
  CI needs no other Cloudflare operation.

### 2–4. The token's effective permissions — unknown

Cloudflare refused token metadata to the only session available: `GET /user/tokens` and
`GET /accounts/<account>/tokens` both answered error 9109 (unauthorized). The wrangler OAuth
grant has no API-token read scope. No CI token value was available, and none was sought, so its
permission groups, resource scope, IP conditions, expiry and last use are unobserved.

What exists instead is setup advice, which is not evidence of the live token:
`apps/updates/README.md` and `setup.sh` tell the owner to create a custom token with
**Workers R2 Storage: Edit** on the account. If the token was made that way, Cloudflare's
documentation says it reaches every R2 bucket in the account and their settings, and no Workers
script permission. Two observations bound the current blast radius without proving the scope:

- The account holds one R2 bucket, `wave-updates` (`wrangler r2 bucket list`).
- The account has two Worker scripts, `wave-sync` and `wave-updates`, and no zones.

Rotation: no rotation policy is documented anywhere in the repo, and the secret has not changed
since it was set.

### 5. The bucket's own exposure — pass

From `wrangler r2 bucket ...` on `wave-updates`:

- Public access through the r2.dev URL is disabled.
- No custom domain is connected.
- No CORS configuration exists (Cloudflare error 10059, "does not exist").
- No event notifications (error 11015) and no lock rules.
- Lifecycle: only the default rule aborting incomplete multipart uploads after 7 days.
- 97 objects, 241 MB, location ENAM, created 2026-11-01.

So the bucket is reachable from outside only through the Worker and through Cloudflare API
credentials. Whether other R2 S3-compatible access keys exist was not observable with this
session and stays unknown.

### 6. The Worker's external routes — pass

Deployed state, from Cloudflare's script metadata:

- `wave-updates` has two versions, both uploaded by wrangler on 2026-11-01 (02:04 and 03:38 UTC);
  the 03:38 one serves 100% of traffic.
- One binding, `UPDATES` → R2 bucket `wave-updates`. No Logpush.
- Reachable at `wave-updates.leonardolp2424.workers.dev`. Preview URLs are enabled, and no custom
  Worker domain or zone route exists.

The deployed bundle, downloaded read-only, answers 405 to anything but GET before it reads the
path, serves only `/v1/manifest`, `/v1/notes`, `/v1/apk` and `/v1/assets/<64 hex>`, and calls the
binding's `get` and `list`, never `put` or `delete`. The older version's source (the commit
before its upload, `c2956efd`) carries the same GET-only guard; its bundle was not downloaded.

Live requests on 2026-11-17, GET and HEAD only:

| Path                                 | GET             | HEAD |
| ------------------------------------ | --------------- | ---- |
| `/v1/manifest` (no protocol headers) | 400             | 405  |
| `/v1/notes?channel=ti&from=0.67.0`   | 200 JSON        | 405  |
| `/v1/apk?channel=ti`                 | 200 signed JSON | 405  |
| `/v1/assets/<64 zeros>`              | 404             | 405  |
| `/v1/assets/..%2Fnotes%2Fti.json`    | 404             | 405  |
| `/notes/ti.json`, `/`                | 404             | 405  |

No PUT, POST or DELETE was sent to production, as the ticket requires. Those methods are covered
by the service tests below.

The R2 binding is not read-only. It can write and delete, and the current source writes one key
from a read: `notes/<channel>.json`, the notes history rebuilt from the stored notes files when
it's absent or unreadable. The external guarantee comes from the route code, and two tests in
`apps/updates/src/service.test.ts` (`the service`) now pin it:

- "lets no outside request upload, replace or remove a stored file": HEAD, OPTIONS, POST, PUT,
  PATCH and DELETE, with a body where the method allows one, on every route and on raw bucket
  keys, all answer 405 and leave every stored object unchanged.
- "writes nothing on a read but the notes history it rebuilds from the stored notes": GETs on
  every route change only `notes/ti.json` and remove nothing.

Both passed against the unchanged service, so they are regression tests, not a fix. To check
they can fail, each was run against a deliberate break: removing the GET-only guard failed the
first, and making the APK route rewrite its object failed the second. Both breaks were reverted.

### 7. Integrity of what phones run — pass

Existing tests cover it, and no change was needed. Each manifest carries every asset's SHA-256
and is signed with `UPDATES_SIGNING_KEY`; assets are stored under their SHA-256; the APK
metadata is signed with the same key and includes the file's SHA-256, which the phone checks
before installing. Write access to the bucket alone therefore can't make phones run new code.
The caveat: the release job holds the Cloudflare token and the signing key in the same
Environment, so a compromise of that job or Environment has both.

### 8. Deployed Worker drift — noted, not a security failure

The deployed version (2026-11-01) predates the 2026-11-06 changes that store a notes history per
channel. Production builds the history from the notes files on every request and writes
nothing; `apps/updates/README.md` describes the newer behaviour. The next deploy will add the
single notes-history write described in finding 6.

### 9. Documentation — fixed here

- `docs/spec.md` (Security) said the token "can write to R2 and nothing else". It now says that is
  the intent and that the actual permissions are unverified, pointing here.
- `apps/updates/README.md` step 3 now marks the token permission as setup advice and says what
  that permission covers.
- `apps/updates/src/service.ts` said the routes only read from storage. It now names the
  notes-history write and says the limit is the code's, not the binding's.

## Evidence still missing

1. The CI token's permission groups, resources, conditions, expiry and last use. Anyone with
   API-token read access to the owner's Cloudflare account can supply them (dashboard › My
   Profile › API Tokens, or `GET /user/tokens` with a token holding API Tokens Read). Record the
   sanitized result here.
2. Whether any R2 S3-compatible access keys exist for the account.
3. A rotation and expiry decision for the token.
4. MFA and audit-log state of the Cloudflare account are outside this ticket's checks and remain
   unverified.

## Decision needed

If the token can't be inspected, the owner must accept or reject this named exception: "The CI
Cloudflare token's scope is unverified; if it is broader than R2 Edit, a leak from the `ti` or
`main` Environment could deploy or change Workers, including the sync Worker that holds the
database credential." Remediation if it proves broader: replace it with a token holding only
Workers R2 Storage: Edit (scoped to `wave-updates` if Cloudflare allows it), set an expiry, then
re-run this check. No rotation, revocation or setting change is authorized by this ticket.
